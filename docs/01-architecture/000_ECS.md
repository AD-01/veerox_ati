# 1. Purpose

This document defines the complete Event-Driven communication model of the Veerox Autonomous Trading Intelligence (ATI) Platform.

It specifies:

- Domain Events
- Integration Events
- System Events
- Event Contracts
- Event Payload Standards
- Event Versioning
- Event Routing
- Event Replay
- Event Correlation
- Event Governance

This document SHALL be the authoritative specification for all asynchronous communication within the platform.

---

# 2. Event Philosophy

Every event represents a **business fact that has already occurred**.

Events SHALL:

- Be immutable.
- Be versioned.
- Be independently consumable.
- Be replayable.
- Be auditable.
- Be idempotent.

Events SHALL NEVER contain business logic.

---

# 3. Event Categories

The platform SHALL define four categories of events.

### Business Events

Represent completed business actions.

Examples:

- StrategySelected
- DecisionGenerated
- OrderSubmitted

---

### Integration Events

Represent interactions with external systems.

Examples:

- MT5AccountSynchronized
- PaymentCompleted
- NewsReceived

---

### System Events

Represent infrastructure and operational activities.

Examples:

- PlatformStarted
- ServiceRecovered
- BackupCompleted

---

### Security Events

Represent authentication, authorization, and security operations.

Examples:

- AuthenticationFailed
- PermissionDenied
- SessionRevoked

---

# 4. Event Naming Convention

Events SHALL use **Past Tense PascalCase**.

Examples:

```text id="event-names"
WorkspaceCreated

StrategyActivated

RiskCalculated

DecisionApproved

OrderSubmitted

PositionClosed

LicenseActivated
```

Future-tense or command-style names SHALL NOT be used.

Invalid examples:

```text id="invalid-events"
CreateWorkspace

ExecuteTrade

CalculateRisk

RunEA
```

---

# 5. Standard Event Envelope

Every event SHALL use the same envelope.

```json id="event-envelope"
{
  "eventId": "evt_01JABC...",
  "eventName": "DecisionGenerated",
  "eventVersion": 1,
  "eventCategory": "Business",
  "aggregateType": "Decision",
  "aggregateId": "dec_123",
  "correlationId": "cor_456",
  "causationId": "cmd_789",
  "organizationId": "org_001",
  "workspaceId": "ws_001",
  "occurredAt": "2026-08-07T10:00:00Z",
  "publishedBy": "decision-service",
  "payload": {}
}
```

Every published event SHALL conform to this structure.

# 6. Event Metadata

Mandatory metadata fields:

| Field | Description |
|--------|-------------|
| eventId | Globally unique identifier |
| eventName | Event type |
| eventVersion | Schema version |
| aggregateType | Aggregate name |
| aggregateId | Aggregate identifier |
| correlationId | End-to-end request trace |
| causationId | Triggering command/event |
| occurredAt | Event timestamp |
| publishedBy | Publishing service |

---

# 7. Event Versioning

Every event SHALL include an integer version.

Example:

```text id="event-versioning"
DecisionGenerated v1

DecisionGenerated v2
```

Breaking payload changes SHALL create a new event version.

Consumers SHALL explicitly support the versions they consume.

---

# 8. Event Routing Principles

The Event Bus SHALL support:

- Publish
- Subscribe
- Retry
- Dead Letter Queue
- Replay
- Event Filtering
- Topic Routing

Events SHALL be routed by **event name**, not by service name.

---

# 9. Topic Naming

Topic format:

```text id="topic-format"
domain.event
```

Examples:

```text id="topics"
identity.user-created

market.market-snapshot-generated

strategy.strategy-selected

risk.risk-calculated

decision.decision-generated

execution.order-submitted

ai.recommendation-generated
```

---

# 10. Delivery Guarantees

The Event Bus SHALL provide:

- At-least-once delivery
- Ordered delivery within an aggregate
- Idempotent consumption
- Retry with exponential backoff
- Dead Letter Queue after configured retry limit

Exactly-once semantics SHALL NOT be assumed.

---

# 11. Event Replay

Authorized administrators SHALL be able to replay events by:

- Aggregate
- Workspace
- Organization
- Time Range
- Event Type

Replay SHALL NOT modify historical events.

Replay SHALL generate new processing outcomes while preserving original event records.

---

# 12. Event Governance

Every new event SHALL define:

- Publishing Domain
- Consuming Domains
- Payload Contract
- Version
- Replay Policy
- Retention Policy
- Security Classification

No event SHALL be introduced without an approved contract.
