# 41. Saga Definitions

The platform SHALL coordinate long-running distributed business workflows using the Saga pattern.

---

## Saga 1 — Autonomous Trade Execution

```text id="saga-trading"
MarketSnapshotGenerated
        │
        ▼
StrategySelected
        │
        ▼
EASelected
        │
        ▼
RiskCalculated
        │
        ▼
DecisionGenerated
        │
        ▼
PolicyPassed
        │
        ▼
ExecutionRequested
        │
        ▼
OrderSubmitted
        │
        ▼
DealExecuted
        │
        ▼
PositionOpened
```

Compensation Actions

- Cancel Pending Execution
- Release Reserved Resources
- Record Failure Event

---

## Saga 2 — Marketplace Purchase

```text id="saga-marketplace"

        │
        ▼

        │
        ▼

        │
        ▼

        │
        ▼
```

- Refund Payment
- Revoke License

---

## Saga 3 — Automatic Strategy Switching

```text id="saga-switch"
MarketRegimeChanged
        │
        ▼

        │
        ▼
StrategySelected
        │
        ▼
EASelected
        │
        ▼

```

If switching fails

↓

Continue previous Strategy

↓

Generate Audit Event

↓

Notify User

# 42. Dead Letter Queue (DLQ)

Events that repeatedly fail SHALL be routed to the Dead Letter Queue.

Stored information:

- Event ID
- Event Name
- Subscriber
- Retry Count
- Failure Reason
- Payload
- Timestamp

DLQ events SHALL support replay after correction.

---

# 43. Event Replay Rules

Replay SHALL support:

- Aggregate Replay
- Workspace Replay
- Organization Replay
- Time-Based Replay
- Event-Type Replay

Replay SHALL preserve:

- Event IDs
- Original Timestamp
- Correlation IDs
- Causation IDs

---

# 44. Event Security Classification

Every event SHALL have a security classification.

| Classification | Description |
|----------------|-------------|
| Public | Safe for external consumption |
| Internal | Platform services only |
| Confidential | Restricted to authorized domains |
| Highly Confidential | Security, Billing, Identity |

Unauthorized services SHALL NOT subscribe to restricted events.

---

# 45. Event Retention Policy

| Event Category | Retention |
|----------------|-----------|
| Business Events | Permanent |
| Integration Events | Permanent |
| Security Events | Permanent |
| Infrastructure Events | 5 Years (minimum) |
| Monitoring Events | Configurable |
| Replay Metadata | Permanent |

---

# 46. Event Catalog Completion Statement

The Event Catalog defines the complete asynchronous communication model of Veerox ATI.

Every domain interaction SHALL occur through versioned, immutable, replayable, and auditable events.

This specification guarantees:

- Loose Coupling
- High Scalability
- Reliable Event Replay
- Full Auditability
- Service Independence
- Deterministic Business Processing
