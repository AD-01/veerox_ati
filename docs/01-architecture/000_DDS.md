# 1. Purpose

This document defines the complete logical and physical database design for the Veerox Autonomous Trading Intelligence (ATI) Platform.

It specifies:

- Database Architecture
- Schema Organization
- Table Definitions
- Relationships
- Constraints
- Indexing Strategy
- Multi-Tenant Model
- Event Store
- Audit Store
- AI Dataset Storage
- Marketplace Storage

This document SHALL be the authoritative source for PostgreSQL schema implementation and Prisma model generation.

---

# 2. Database Philosophy

The database SHALL support:

- High Consistency
- High Availability
- Event-Driven Architecture
- Domain-Driven Design
- Multi-Tenancy
- Horizontal Growth
- Auditability
- AI Readiness

The database SHALL store business state.

Business rules SHALL remain in the Domain Layer.

# 4. Database Architecture

The platform SHALL use a **Schema-per-Domain** logical organization inside a single PostgreSQL cluster.

```text id="db-arch-001"
PostgreSQL
│
├── identity
├── organization
├── workspace
├── market
├── strategy
├── expert_advisor
├── risk
├── portfolio
├── decision
├── policy
├── execution
├── connector
├── marketplace
├── licensing
├── billing
├── ai
├── notification
├── audit
├── analytics
├── event_store
└── shared
```

Each schema SHALL own its data.

Cross-schema writes SHALL occur only through the application layer.

# 5. Naming Standards

## Tables

Plural nouns

Examples

```text id="tbl-example"
users
organizations
workspaces
strategies
orders
positions
licenses
```

---

## Primary Keys

Every table SHALL contain:

```text id="pk-example"
id UUID PRIMARY KEY
```

UUID v7 SHOULD be used where supported.

---

## Foreign Keys

Standard format

```text id="fk-example"
user_id

workspace_id

strategy_id

portfolio_id
```

---

## Timestamp Columns

Every business table SHALL include:

```text id="ts-example"
created_at

updated_at
```

Optional:

```text id="soft-delete"
deleted_at
```

Soft deletion SHALL be used only where business requirements permit.

---

# 6. Multi-Tenant Strategy

Every tenant-owned entity SHALL include:

```text id="tenant-fields"
organization_id

workspace_id
```

This ensures strict tenant isolation.

No query SHALL return data outside the authorized tenant scope.

---

# 7. Shared Base Columns

Every business entity SHALL include the following fields unless explicitly exempted:

| Column | Type | Description |
|---------|------|-------------|
| id | UUID | Primary Key |
| created_at | TIMESTAMP | Creation timestamp |
| updated_at | TIMESTAMP | Last update timestamp |
| created_by | UUID | Creator |
| updated_by | UUID | Last modifier |
| version | INTEGER | Optimistic locking |
| status | VARCHAR | Business status |

# 9. Relationship Rules

The platform SHALL use:

- One-to-One
- One-to-Many
- Many-to-Many (junction tables)

No polymorphic relationships SHALL be permitted.

Every relationship SHALL use explicit foreign keys.

---

# 10. Constraints

Every table SHALL enforce:

- Primary Key
- Foreign Key
- Unique Constraints
- Check Constraints
- Not Null Constraints
- Optimistic Versioning

Business validation SHALL NOT rely solely on database constraints.

---

# 11. Indexing Strategy

Every table SHALL have:

### Clustered Index

Primary Key

---

### Secondary Indexes

Frequently searched fields.

Examples

```text id="index-example"
organization_id

workspace_id

symbol

status

created_at
```

---

### Composite Indexes

Example

```text id="composite-index"
(symbol, timeframe)

(strategy_id, version)

(workspace_id, status)

(account_id, symbol)
```

---

### Partial Indexes

Used where appropriate for:

- Active Records
- Open Positions
- Active Strategies

---

# 12. Data Integrity Rules

The platform SHALL guarantee:

- Referential Integrity
- Transaction Consistency
- Optimistic Locking
- Event Consistency
- Immutable History

No orphaned business records SHALL exist.

---

# 13. Database Security

The database SHALL implement:

- Row-Level Security (RLS) where applicable
- Read-only Roles
- Service Roles
- Migration Roles
- Backup Roles

Application users SHALL NOT connect directly to PostgreSQL.

---

# 14. Database Principles

The database SHALL remain:

- Normalized for transactional domains
- Optimized for read models where required
- Event-compatible
- Audit-friendly
- AI-ready
- Horizontally extensible

The schema SHALL evolve through version-controlled migrations only.
